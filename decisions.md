# Decision Log

This is an append-only log of key architectural, product, and design decisions and their rationale. It provides historical context for how the project evolved — specs show the current state, this log shows *why*.

**Agent rule:** Do NOT write directly to this file during a session. Instead, write new entries to `decisions-pending.md` using the format below. The `scripts/merge-decisions.sh` pre-commit hook merges all pending entries into this file at commit time, then deletes `decisions-pending.md`. This keeps diffs clean and avoids churn on a shared file during multi-step sessions.

## Entry Format

```
## YYYY-MM-DD — [Decision Title]
**Decision**: [What was decided]
**Rationale**: [Why]
**Alternatives considered**: [What else was evaluated]
```

## 2026-04-19 — Per-migration version bump (not whole-run atomic)
**Decision**: `pdeqVersion` is bumped after each individual migration completes cleanly, rather than deferred until every pending migration in a batch succeeds.
**Rationale**: Directly realizes the design's observable failure-output behavior ("Recorded pdeq version: 0.3.0 — advanced from 0.2.1, 0.3.0 applied cleanly"), makes partial runs trivially resumable (re-running `/migrate` naturally picks up from the new recorded version, no special resume flag needed), and avoids any rollback machinery. The only cost is that `pdeq.json` is rewritten N times across an N-migration batch, which is harmless and arguably helpful (partial application is visible in `git status`).
**Alternatives considered**: Whole-run atomic bump — defer version writes until all migrations in a batch succeed. Rejected because failure mid-batch either requires rolling back already-applied mechanical/semantic edits (complex, error-prone) or leaves the recorded version lagging behind the actual filesystem state (violates the design's explicit "recorded version advanced to last fully-applied migration" output).
## 2026-04-19 — Scope enforcement via author discipline + post-run audit, not filesystem sandbox
**Decision**: Migration scope is enforced by (a) a required `scope:` frontmatter field that authors declare up front and (b) a post-run `audit-scope` subcommand that diffs `git status` against the declared scope and fails if writes landed outside. No sandboxed filesystem, no write-interception shim.
**Rationale**: A real sandbox (container, chroot, LD_PRELOAD write interceptor) is heavy, platform-specific, and fundamentally incompatible with the hybrid shell-plus-Claude execution model — the semantic block runs in Claude's context and cannot be sandboxed the same way as a shell block, so a sandboxed mechanical + unsandboxed semantic split would be worse than a uniform honor-system policy. The trust model (migration shell code is checked into the pdeq repo by maintainers) already assumes trust; a post-run audit catches the realistic failure mode (author forgets to declare broader scope), and the design's `scope:` frontmatter field makes violations reviewable at PR time.
**Alternatives considered**: (1) Filesystem sandbox — rejected as disproportionate for v1 and incompatible with the semantic block. (2) No scope enforcement at all — rejected because product requires `FR-migrations-scoped-writes` and `AC-migrations-scope-respected` as observable properties.
## 2026-04-19 — `/migrate` orchestration lives in markdown (Claude-driven), not pure shell
**Decision**: The `/migrate` runner is split: a markdown slash-command file (`.claude/commands/migrate.md`) orchestrates the per-migration loop in Claude's execution context, delegating deterministic work (version math, file discovery, frontmatter parsing, idempotent mechanical edits, version bumps) to subcommands of `scripts/migrate.sh`. The shell script alone is not the runner.
**Rationale**: Semantic blocks fundamentally require a live AI agent to read file context and produce judgment-driven edits. A pure shell orchestrator cannot hand control back to Claude mid-run. Conversely, shell is the right tool for version math, JSON field rewrites, and filesystem discovery — fast, testable, no runtime dependencies. Splitting the runner along this boundary keeps each half in its natural lane, matches the convention already established by `/kickoff` and `/bootstrap` (markdown orchestrator plus shell helpers), and gives QA a shell-testable surface for the deterministic half.
**Alternatives considered**: (1) Pure shell runner that shells out to `claude` CLI for semantic blocks — rejected because it couples the runner to a specific CLI invocation path, complicates testing, and breaks the "runner is a slash command" mental model. (2) Pure Claude-driven runner with no shell helpers — rejected because version math and JSON edits need to be deterministic and shell-testable without invoking an agent.
## 2026-04-19 — Bootstrap chain pins pdeq to N-1 (not N or N-2)
**Decision**: The pdeq repository adds itself as a submodule pinned to the previous stable release (N-1). On each release, the maintainer bumps the self-pin from N-1 to the newly-previous N-1 (i.e., the version just before the one being released) and runs `/migrate` against pdeq's own specs.
**Rationale**: Pinning to the in-development version (N) defeats the dogfood property — framework edits under active development would immediately take effect for the maintainer's own kickoff and status runs, making it impossible to test that the framework evolves safely under its own tooling. N-2 introduces unnecessary lag with no additional guarantee. N-1 is the minimum distance that preserves "pdeq is managed by a stable pdeq" while keeping the lag short enough that the maintainer exercises the latest stable behavior on their own repo.
**Alternatives considered**: (1) N (self-pin to in-development version) — rejected as described. (2) N-2 — rejected as unnecessary lag with no benefit. (3) Unpinned (track main) — rejected because a moving pin breaks the reproducibility that migrations are supposed to provide.
## 2026-04-19 — Breaking-change gate runs in `commit-msg`, not `pre-commit`
**Decision**: The `scripts/audit-migrations.sh` hook is invoked from the `commit-msg` git hook, not from `pre-commit`, so it can read the finalized commit message and detect the `pdeq-migration: none-required` trailer deterministically.
**Rationale**: The trailer override (design Surface 8 option C) requires reading the commit message. In `pre-commit`, the message only exists in `COMMIT_EDITMSG` during interactive commits; `git commit -m "..."` bypasses that path. `commit-msg` runs after the message is finalized and receives its path as `$1`, making trailer detection universal. The other pdeq hooks (`audit-traceability.sh`, `merge-decisions.sh`) continue to run in `pre-commit` where they belong.
**Alternatives considered**: (1) `pre-commit` reading `COMMIT_EDITMSG` — rejected as fragile with `-m`. (2) Check trailer only in CI, not locally — rejected because the gate needs to block at commit time, not after push.
## 2026-04-19 — Semver comparison uses `sort -V`, not a hand-rolled comparator
**Decision**: `scripts/migrate.sh` uses `sort -V` as the semver comparator. Two-value comparison is implemented by piping the two versions through `sort -V` and checking which came first.
**Rationale**: `sort -V` is POSIX-available on both macOS and Linux, correctly orders plain MAJOR.MINOR.PATCH including numeric-not-lexicographic segment handling (`0.3.0 < 0.10.0`), and keeps the script dependency-free. A hand-rolled comparator is more code and more edge cases to test for no benefit.
**Alternatives considered**: Hand-rolled `IFS=.` comparator — rejected for complexity. `semver` npm package — rejected because it requires node, breaking the zero-runtime-dependency constraint.
**Limitation**: `sort -V` does not correctly order pre-release suffixes (`0.4.0-rc.1`). Pre-release versions are out of scope for v1 and flagged in the engineering spec's Open Technical Questions if pdeq later ships RCs.
## 2026-04-23 — Requirement↔code mapping uses hybrid inline-marker + Code Map + audit
**Decision**: Requirement-to-code traceability is enforced by three layers: (1) inline comment markers in code citing requirement slugs at the implementation site, (2) a Code Map section in each platform's engineering spec listing planned code locations per slug, and (3) an extension of `scripts/audit-traceability.sh` that scans for markers, reconciles against product slugs and planned paths, and populates a code-locations column in `index.md`. Inline markers are authoritative; the Code Map captures intent; the audit reconciles both.
**Rationale**: Each layer catches the others' drift. Inline markers can't drift from the code they annotate (they move with the block), but they depend on author discipline — the audit catches forgotten or misspelled markers. The Code Map captures planning-time intent before code exists and surfaces stale paths when files are deleted or renamed, but would rot without an audit to force review. The audit alone (grep heuristic with no markers) would return arbitrary source lines containing slug-like strings — unreliable. Together they give agents a single lookup (`index.md` code column) that is automatically kept current by the pre-commit pipeline.
**Alternatives considered**: (1) Pure audit-driven (heuristic grep for "related" code) — rejected because no heuristic is reliable enough for agents to trust without verification. (2) Pure engineering-spec mapping (Code Map only, no markers) — rejected because mappings rot fast when code moves and there is no forcing function to update them at the moment of change. (3) Separate mapping file (e.g., `code-map.json` at repo root) — rejected because it duplicates information that already belongs with the code and the engineering spec, and introduces a third file that can drift. The hybrid approach is strictly redundant by design.
## 2026-04-23 — Slug retirement forces same-commit marker cleanup (no grace)
**Decision**: When a product-spec change removes a slug that still has markers in the code, the traceability audit blocks the commit immediately. There is no grace period for retirement — the slug-removal change and the marker-cleanup change must land together.
**Rationale**: Retirement is a deliberate authorial act, unlike the "spec written before implementation" case the grace period exists for. The author already has the whole picture at the moment they're removing the slug, so forcing the code cleanup into the same change set keeps the markdown-to-code invariant true at every commit and eliminates a class of "which repo state is real" ambiguity for downstream agents. A grace-on-retirement policy would require tracking "slug is being retired as of commit X, block after N more commits" state outside the repo — expensive and prone to bugs for a scenario that should be rare.
**Alternatives considered**: Grace-on-retirement (warn for one release, then block). Rejected — adds state, adds a slow-leak failure mode (forgotten cleanup), and defers work the author is best positioned to do now.
## 2026-04-23 — Grace period measured in commits since slug introduction, against product spec's git history
**Decision**: For the coverage grace period on newly-introduced slugs, engineering will use the number of commits that have modified the product spec file since the slug's introductory commit as the threshold signal (concrete count to be pinned in the engineering spec). Measurement is taken from `git log` on the product spec file, not from wall-clock time or release tags.
**Rationale**: Git-native, deterministic, survives clones, needs no config file or external clock. Correlates with author activity (commits = real work on the spec) rather than calendar time (which penalizes slow projects and rewards fast ones artificially). Measuring commits on the product spec file specifically, rather than global repo commits, ignores unrelated work — the grace window reflects "how much spec work has happened since this FR was added," which is the meaningful signal.
**Alternatives considered**: (1) Wall-clock days — rejected because it's not reproducible and doesn't scale across active/dormant projects. (2) pdeq release tags — rejected because most consumer repos don't tag on pdeq release cadence. (3) Global commit count — rejected because unrelated commits would burn down the grace window for reasons orthogonal to the spec.
## 2026-04-23 — Hook installation uses `git config core.hooksPath` pointing at tracked hook dir
**Decision**: `scripts/init.sh` and the `/bootstrap` command set `core.hooksPath` to a tracked directory inside the pdeq install (e.g., `.pdeq/hooks/` for consumer installs, `scripts/hooks/` for the pdeq repo self-host). The directory contains executable `pre-commit`, `commit-msg`, etc. stubs that delegate to `scripts/audit-*.sh` and `scripts/merge-decisions.sh`. A `--skip-hooks` flag on `init.sh` and an equivalent prompt in `/bootstrap` lets CI/container contexts opt out.
**Rationale**: `core.hooksPath` is a single git config, survives clones across all developers by virtue of the install step that runs once per clone, and keeps the hook scripts themselves tracked in the repo — so adding or changing a hook is a code review, not a per-developer re-install. This matches pdeq's tracked-deterministic-zero-runtime-deps philosophy and aligns with how `/kickoff` and `/migrate` already work. Symlink-into-`.git/hooks/` was considered but rejected as drift-prone: nothing forces a re-install after new hooks are added. Third-party frameworks (pre-commit.com) were rejected as introducing a Python dependency and a parallel tool consumers must learn.
**Alternatives considered**: (1) `scripts/install-hooks.sh` that symlinks into `.git/hooks/` — rejected because it must be rerun after every clone and every new-hook addition, and there's no forcing function. (2) `pre-commit.com` framework — rejected as a Python dependency that conflicts with the zero-runtime-deps constraint. (3) Layered hooks (pdeq's hooks chain into a user-provided `.git/hooks-local/*`) — accepted as a non-blocking follow-up to let consumers layer their own hooks without fighting the pdeq install; not required for v1.

## 2026-04-26 — Phase 5b scope rule anchored on first declaration line
**Decision**: The audit's marker scope check (Phase 5b) flags a marker iff the file contains at least one named-unit declaration AND the marker line is more than one line above the first such declaration. The prior heuristic (`marker_line ≤ 5` plus a function-regex grep) is removed.
**Rationale**: The line-position heuristic produced false positives in short components whose first declaration starts on line 1–3 — a marker correctly placed inside the function body would still trip the warning because its absolute line was ≤ 5. Anchoring against `first_decl_line` instead of an absolute line count eliminates that false-positive class without weakening the catch for genuine file-top placement (the original target antipattern). Position is now judged structurally, against where named units actually begin.
**Alternatives considered**: (1) Raise the line-position threshold (e.g., line ≤ 10) — only delays the false positive into longer components without fixing the underlying mismatch between absolute line count and structural placement. (2) Parse the file with a real tokenizer — disproportionate for what is a deliberately loose heuristic check; the audit's job is to catch obvious file-top antipatterns, not to validate every structural placement. (3) Remove Phase 5b entirely — discards a useful warning class for genuine file-top markers. The first-declaration-line approach keeps the warning where it earned its keep and discards it where it didn't.

## 2026-04-26 — `/pdeq-update` is the unified upgrade entrypoint; bump-then-migrate auto-chains; symlink logic factored to a shared helper
**Decision**: The consumer-facing upgrade surface is the slash command `/pdeq-update`. It advances the pinned `.pdeq/` submodule reference, runs a symlink sync, and chains into `/migrate` as a single auto-run flow with no intermediate confirmation prompt. Implementation extracts the symlink-creation logic that already lives inside `scripts/init.sh` Steps 5–6 into a shared helper, `scripts/sync-symlinks.sh`, which both `init.sh` (without `--prune`) and `.claude/commands/pdeq-update.md` (with `--prune --json`) call. Inside the pdeq repository itself, `/pdeq-update` detects self-host context and refuses with a maintainer-flow message that points the maintainer at the manual self-pin advance.
**Rationale**: The command is `/pdeq-update` rather than the bare-verb `/update` because the `pdeq-` prefix namespaces pdeq commands for discoverability and clarity in projects that have many slash commands from different sources. The prefix makes ownership unambiguous at a glance and avoids collision with whatever bare-verb commands a consumer's other tooling may ship. The chained migration is auto-run rather than prompted because the consumer has already opted in by typing `/pdeq-update` — a confirmation step would split one decision into two without changing the outcome on the happy path, and recovery on mid-migration failure flows through the existing `/migrate` failure surface unchanged. The symlink logic is factored into a separate script rather than inlined in both call sites because the rules (which directories, what target paths, when to prune) are non-trivial and duplicated logic in shell drifts fast — a single helper with a `--prune` flag keeps init and update behaving identically and gives QA one surface to test instead of two.
**Forward-looking note**: This name choice anticipates a future namespace convention where all pdeq slash commands carry the `pdeq-` prefix (e.g., `/pdeq-kickoff`, `/pdeq-status`, `/pdeq-migrate`, `/pdeq-impact`, `/pdeq-bootstrap`). Renaming the existing bare-verb commands is a separate breaking change deferred to a follow-up migration; introducing the upgrade entrypoint with the prefix sets the precedent without forcing the wider rename now.
**Alternatives considered**: (1) Bare `/update` — rejected because the prefix-less name does not signal pdeq ownership, can collide with other tooling, and would lock pdeq into a bare-verb convention just as the project moves toward namespace-explicit commands. (2) `/migrate --bump` — rejected because it buries the upgrade entrypoint under a flag on a different command, violating the discoverability goal and forcing consumers to learn migrate's argument surface to perform an upgrade. (3) Prompting before chaining the migration run — rejected as a redundant confirmation step that splits one decision into two with no information gain. (4) Inlining the symlink logic in both `init.sh` and `pdeq-update.md` — rejected because the rules duplicate and would drift; one helper is the only way to keep init and update aligned. (5) Allowing `/pdeq-update` to run inside the pdeq repo — rejected because pdeq's `.pdeq/` submodule is intentionally pinned to N-1 for the bootstrap chain, and bumping it via `/pdeq-update` would defeat the dogfood property; the maintainer flow is a deliberate manual self-pin advance, not an automated `/pdeq-update`. (6) Renaming all existing bare-verb pdeq commands to the `pdeq-` prefix at the same time as introducing this entrypoint — deferred. That is a separate breaking change requiring its own migration; this entry only introduces the prefix for the new command.
## 2026-04-27 — Namespace all pdeq slash commands with `pdeq-` prefix; ship as breaking 0.3.0 with migration
**Decision**: All pdeq-installed slash commands carry the `pdeq-` prefix. The six pre-existing bare-verb commands (`/bootstrap`, `/impact`, `/kickoff`, `/migrate`, `/status`, `/visualize`) are renamed in place to `/pdeq-bootstrap`, `/pdeq-impact`, `/pdeq-kickoff`, `/pdeq-migrate`, `/pdeq-status`, `/pdeq-visualize`. The convention is recorded in `product/cli-conventions.md` as `FR-cli-naming-prefix`, propagated to consumers via migration `migrations/0.3.0.md`, and shipped as the breaking 0.3.0 release. The 0.3.0 migration's mechanical block detects pdeq-managed symlinks under `.claude/commands/` and renames them in-place; consumer-customized regular files are left alone with a one-line warning.
**Rationale**: A consumer's slash-command palette mixed pdeq commands with project-local commands and other tooling's commands with no namespace marker — typing `/m` could surface pdeq's `/migrate` alongside an unrelated `/migrate-data` from a project script, and a consumer browsing the palette had no way to filter to "pdeq commands." The prefix solves both problems: typing `/pdeq` tab-completes the entire pdeq surface, and any command not starting with `pdeq-` is by definition not pdeq's. This also resolves the asymmetry that began with the earlier `/pdeq-update` decision (2026-04-26), where the new command got the prefix but the existing six did not. Shipping the rename as a breaking 0.3.0 with a migration is the standard pdeq upgrade path — the migration system exists precisely so that breaking renames can be delivered to consumer projects without requiring manual edits.
**Alternatives considered**: (1) Keep bare-verb names — rejected because it preserves the discoverability and collision problems. (2) Prefix only newly-added commands going forward (the position taken in the 2026-04-26 decision) — rejected because it leaves the inconsistency in place permanently and makes "is this command pdeq's?" a question with two answers depending on the command's age. (3) Rename without a migration, requiring consumers to manually rename their symlinks — rejected because manual renames defeat the purpose of having a migration system, and consumers who skip the manual step would silently lose their pdeq commands when a future submodule bump removed the old names from `.pdeq/.claude/commands/`. (4) A non-`pdeq-` prefix (e.g., `pd-`, `:pdeq`, `pdeq.`) — rejected because `pdeq-` is unambiguous, the project name itself, and matches the precedent already set by `/pdeq-update`.

## 2026-05-16 — Harness-agnostic install: bash-internal adapter over `block/ai-rules`
**Decision.** Implement multi-harness install support as a bash-internal harness adapter table inside `scripts/init.sh`, rather than adopting `block/ai-rules` as the materialization engine.
**Context.** Block's `ai-rules` CLI covers the same conceptual surface (per-harness rules/commands/skills generation) and ships with 11 supported harnesses. The alternatives were (a) vendor it as an install dependency, (b) write our own equivalent in bash.
**Rationale.** Three factors decided it: (1) pdeq's existing install-dependency floor is `git + bash`, and adding a Rust binary as a hard prerequisite for `init.sh` is a real friction tax that outweighs the convenience for the v1 harness set (claude, codex, pi); (2) `ai-rules` does not currently support Pi, which is the original motivator for going harness-agnostic; (3) pdeq's surface is small enough — one canonical agent file per lane, six slash commands, one skill — that the bash adapter table is ~60 lines and fits the project's existing style. We can reconsider adopting `ai-rules` later if pdeq's surface grows or if the harness adapter table starts repeating logic that `ai-rules` already implements.
## 2026-05-16 — AGENTS.md as canonical, CLAUDE.md as Claude-specific compatibility view
**Decision.** The pdeq submodule's authoritative agent-instructions filename at every lane is `AGENTS.md`. Consumer-project `CLAUDE.md` files are emitted by the installer only when `claude` is in the harness list and are one-line `@import` references to the canonical `AGENTS.md`. Other harnesses get `AGENTS.md` files as symlinks pointing at the canonical source.
**Context.** AGENTS.md is the de facto cross-harness convention (Codex, Copilot, Goose, Cline, Cursor, Pi all read it). CLAUDE.md is Claude-specific. Earlier the submodule used CLAUDE.md as the source of truth, which forced any non-Claude harness to either re-implement the file or be left without pdeq prose.
**Rationale.** Inverting the canonical/compatibility relationship lets pdeq target the broad convention as the source of truth and limit Claude-specific behavior (`@import` syntax, `.claude/commands/` path) to the materialization layer. The Claude `@import` form is preserved so consumers can still append project-specific instructions below the import — a behavior `init.sh` already relies on.
## 2026-05-16 — Hard cutover at 0.4.0; no transitional dual-layout window
**Decision.** Pdeq 0.4.0 is a single hard cutover. The 0.4.0 migration removes the old layout (CLAUDE.md in submodule, `.claude/agents/bootstrap-*` files, `.claude/commands/` as canonical source) in one step. There is no soft-transition release that supports both layouts.
**Context.** The alternative was to ship 0.4.0 with both old and new file shapes accepted, then deprecate the old in 0.5.0 or later. That would require dual-layout code in `init.sh` and a longer-lived compatibility surface in every downstream tool.
**Rationale.** Pdeq's migration system (`product/migrations.md`) was designed for exactly this kind of breaking change — the consumer's explicit invocation of `/pdeq-migrate` is the supported upgrade flow. A soft-transition window would carry compatibility code indefinitely, dilute the contract, and add edge cases (consumer half-migrates, two harnesses see different prose) for no consumer benefit. The hard cutover is consistent with the precedent set by the 0.3.0 command-rename migration.
## 2026-05-16 — Bootstrap subagent prompts folded into the slash command
**Decision.** The `.claude/agents/bootstrap-analyzer/*` and `.claude/agents/bootstrap-generator/*` subagent definition files are deleted in 0.4.0. Their prompts move inline into `pdeq-rules/commands/pdeq-bootstrap.md` so the bootstrap workflow does not depend on any harness's ability to load named subagent definitions.
**Context.** Pre-0.4.0, `pdeq-bootstrap.md` invokes Claude Code's `Task` tool with named subagents that live in `.claude/agents/`. Codex CLI and Pi do not have an equivalent subagent definition format.
**Rationale.** The inline form is harness-portable. Harnesses that support spawning subagents internally (Claude Code) can still do so — the prompts are simply visible in the command file rather than in a separate file the harness has to know how to discover and load. This costs some prompt length but eliminates a per-harness assumption.

## 2026-05-18 — `/pdeq-update` chained migration is prompted, not auto-run
**Decision**: After the submodule bump succeeds, `/pdeq-update` prints the pending-migrations summary and a single cyan `?` prompt (`? Apply pending migrations now? [Y/n]:`). A bare Enter / `y` / `yes` accepts and the chained `/pdeq-migrate` runs; anything else (including `n`, `no`, an empty non-default token, or any unexpected agent reply) declines and the runner exits via Surface 15, leaving the bump in place and naming `/pdeq-migrate` as the follow-up. The prompt is skipped automatically when the pending set is empty (pure non-breaking advance) — there is no review checkpoint to gate when no mechanical or semantic edit is queued.
**Rationale**: Reverses the previous resolution (auto-run). Two classes of mutation happen back-to-back in a single `/pdeq-update`: the bump (submodule pointer + symlink reconciliation) and the chained migration (mechanical scripts + semantic agent edits across the specs tree). The bump is reviewable on its own via `git diff .pdeq .gitmodules scripts/ .claude/commands/` and a consumer may legitimately want to commit the bump separately from the migration, or look at what a release actually shipped before authorizing the migration loop to touch their specs. The previous "one decision, one keystroke" framing assumed the consumer would never have a reason to want to inspect mid-flow; field experience with the autopilot project (where the chain would have done its work before the user could see what the bump alone changed) showed otherwise. Cost on the happy path is one keystroke (Enter accepts), which is cheap.
**Alternatives considered**: (1) Keep auto-run (the previous resolution) — rejected for the reasons above. (2) Add a `--yes` flag to opt out of the prompt — rejected because `/pdeq-update` is invoked from an interactive agent session by design and headless flows should drive the underlying shell helpers directly; a `--yes` flag would create a parallel "expert path" that obscures the design's review-checkpoint intent. (3) Configurable default via `pdeq.json` — rejected as premature; the project does not yet have other behavior-toggle config and adding one for this single choice would set an awkward precedent.

## 2026-06-30 — Lane discipline enforced by two layers (lexical backstop + agent lane review)
**Decision.** Lane discipline is enforced by two complementary layers rather than a single mechanism. Layer 1 is the deterministic `scripts/audit-lanes.sh` keyword scan, kept as a cheap, agent-free backstop and made project-tunable via a `laneAudit` object in `pdeq.json`. Layer 2 is a new agent-run **Lane Reviewer** (root `AGENTS.md` §Quality Subagents), invoked in `/pdeq-kickoff` Step 4 and any standalone product-spec review, which reasons about structural bleed and classifies findings by category and severity.
**Context.** In a real project (coffee-shop) two classes of bleed passed the fixed-keyword audit: vendor/protocol bleed (Square, OAuth, "authorization code exchange", CSRF) and host bleed (the CLI treated as the product, "coffee auth login", "exits non-zero"). The bleed was often structural, not lexical — "authorization code exchange" reads as OAuth-shaped without the word OAuth — and a grep cannot distinguish a violation from a legitimate overview or per-host-NFR mention.
**Rationale.** A keyword list can only catch words someone thought to list, and can never see structure or judge context. But it is cheap, deterministic, and CI-safe, which the agent pass is not. Keeping both — the grep as a fast lexical net, the agent as the real principle enforcement — gets determinism where it is possible and judgement where it is required, without pretending either alone is sufficient. The docs state explicitly that a clean `audit-lanes.sh` run does not imply an in-lane spec.
**Alternatives considered.** (1) Expand the hardcoded keyword list — rejected; it never generalizes to unlisted vendors/protocols and still cannot see structural bleed. (2) Replace the bash audit with the agent pass entirely — rejected; loses the deterministic, no-LLM commit-time/CI guard. (3) Make the agent pass a blocking commit-time gate — rejected; it is non-deterministic and must not wedge a commit.
## 2026-06-30 — `laneAudit` is a categorized object that extends (not replaces) built-in defaults
**Decision.** The project-tunable term list in `pdeq.json` is a `laneAudit` object with four string-array categories — `vendors`, `protocols`, `platforms`, `libraries`. Each array **extends** the built-in default term list rather than replacing it. `audit-lanes.sh` reads it with inline `python3` (no `jq`), unions all four categories into the technology-name scan, and regex-escapes each term so it matches literally.
**Context.** The audit needed to be meaningful per project (each has its own vendors/protocols) without editing the shared submodule, and without silencing the shipped guard. The shape choice was a flat term array vs a categorized object.
**Rationale.** The categorized object is self-documenting — a maintainer reading `pdeq.json` sees *why* each term is listed — and mirrors the Lane Reviewer's red-flag taxonomy, so the two layers speak the same vocabulary. Extend-not-replace guarantees back-compatibility: a project that adds its vendors never loses the built-in defaults, and a project with no `laneAudit` key behaves exactly as before.
**Alternatives considered.** (1) Flat `laneTerms` array — rejected; simpler to grep but loses per-category self-documentation and the taxonomy alignment. (2) Replace-semantics (project list overrides defaults) — rejected; it silently disables the shipped guard the moment a project configures anything.
## 2026-06-30 — `audit-lanes.sh` runs warn-only in pre-commit and scans via `python3 re`, not `grep -P`
**Decision.** `audit-lanes.sh` is wired into `hooks/pre-commit` as a warn-only step (`… || true`) that never blocks a commit, while keeping its standalone `exit 1` for on-demand/CI use. Its scanning is done through a `python3 re` helper (`pcre_scan`) rather than `grep -nP`.
**Context.** The script previously used `grep -nP`. macOS ships BSD grep, which rejects `-P` outright, and the script's `2>/dev/null || true` swallowed the error — so the audit **silently no-op'd on macOS**, which is exactly where the pre-commit hook runs. Turning it into a warn-only commit-time step made that latent defect matter.
**Rationale.** Warn-only reflects the heuristic nature of a keyword scan: false positives must not wedge a legitimate change, and the real enforcement is the agent pass anyway. Routing the scan through `python3` (already a hard pdeq dependency, used by `audit-traceability.sh`) makes the backstop deterministic and identical across macOS and Linux with no new dependency, satisfying the determinism NFR. The first working scan surfaced 8 pre-existing findings in pdeq's own specs (`visualize.md`, `harness-agnostic.md`) — left as-is (out of scope; warn-only means no block) and a good demonstration the layer now works.
**Alternatives considered.** (1) Blocking pre-commit guard — rejected; a heuristic scan producing false positives should not block. (2) Keep `grep -P` and require GNU grep — rejected; adds a toolchain prerequisite and leaves macOS silently broken. (3) Leave `audit-lanes.sh` standalone-only (not in the hook) — rejected; obvious lexical leaks should surface on every commit, cheaply.
## 2026-06-30 — Lane discipline ships in 0.5.0 with a non-breaking propagation migration
**Decision.** Lane discipline releases as pdeq 0.5.0 with a `migrations/0.5.0.md` whose front-matter is `breaking: false`. The migration's Mechanical block idempotently seeds an empty `laneAudit` scaffold into the consumer's `pdeq.json` (only if absent); its Semantic block runs the Lane Reviewer over `product/**/*.md` in report-only mode (no edits, `updated 0`). `VERSION` bumps 0.4.0 → 0.5.0; the repo dogfoods the seed into its own `pdeq.json`.
**Context.** `laneAudit` is optional and the backstop's defaults preserve prior behavior, so a consumer stays conformant on a bare bump — by the glossary's definition the change is non-breaking. But the feature does not auto-propagate: nothing seeds the config or reviews existing specs. The user wanted the update to do both. pdeq's migration model pairs migrations with *breaking* MINOR/MAJOR bumps (`FR-migrations-one-per-version`: "non-breaking versions have no migration"); the commit-msg gate over-classifies any MINOR bump as breaking and requires a matching migration file.
**Rationale.** Shipping the migration on the MINOR bump satisfies the gate (which checks file presence, not the `breaking:` field) and gives the propagation the user asked for. `breaking: false` is kept because it is the honest label — a consumer who never runs the migration remains conformant. The runner still applies the file (pending-window + file presence, independent of the flag), so the seed + report run on `/pdeq-migrate`. The Semantic pass is report-only so a requirements-altering rewrite is never done unattended.
**Known tension / follow-up.** This is a `breaking: false` migration, which stretches `FR-migrations-one-per-version` ("non-breaking versions have no migration"). The clean fix is to formally introduce an *advisory / non-breaking migration* class in `product/migrations.md` (option C from the propagation decision) — deferred to its own kickoff rather than smuggled into this change.
**Alternatives considered.** (1) `breaking: true` — internally tidier (breaking version ↔ migration) but mislabels a change that leaves consumers conformant. (2) No migration + `pdeq-migration: none-required` trailer — the model's supported non-breaking path, but it drops the config seed and the conformance review the user wants. (3) Auto-rewording Semantic pass — rejected; product specs are the source of truth and unattended rewrites risk changing requirement meaning.

## 2026-07-01 — Formalize the advisory (non-breaking) migration class
**Decision.** `product/migrations.md` now defines two operational senses of "breaking" and an **advisory migration** class. *Lineage-breaking* (a MINOR/MAJOR bump) is the semver property the runner (`lineage-breaking`) and the gate (`is_breaking_bump`) act on; *consumer-breaking* is the impact judgment recorded in a migration's `breaking:` frontmatter, which the tooling does not read. An advisory migration (`breaking: false`) rides a lineage-breaking release that is not consumer-breaking: its transforms are optional and idempotent, so skipping it (or a report-only semantic pass) leaves the project conformant. New `FR-migrations-advisory-class` + `AC-migrations-advisory-applied` / `AC-migrations-advisory-conformant`; `FR-migrations-one-per-version` reworded to "one file per lineage-breaking version" so advisory migrations no longer contradict it.
**Context.** 0.5.0 (lane-discipline) shipped a `breaking: false` migration to propagate an optional config seed + report-only review. That contradicted the old wording "non-breaking versions have no migration." Investigation showed the tooling already applies such migrations correctly — the `breaking:` frontmatter is informational and unread by the runner/gate, which key on semver — so the gap was purely in the product spec's language.
**Rationale.** The reconciliation is documentation-only: no runner or gate change was needed, because a MINOR bump already requires + applies a migration file regardless of the `breaking:` flag. Naming the two senses of "breaking" removes the ambiguity that made 0.5.0 look like a rule violation, and the advisory class gives future non-consumer-breaking MINOR releases a sanctioned way to propagate optional setup. 0.5.0 is retroactively the first advisory migration.
**Alternatives considered.** (1) Make the runner/gate read the `breaking:` frontmatter and treat `false` specially — rejected; it works today on semver alone, and coupling application to a human-facing flag adds a failure mode (mislabeled flag skips a needed migration) for no benefit. (2) Ban non-consumer-breaking migrations and require the `pdeq-migration: none-required` trailer instead — rejected; that drops the ability to propagate an optional seed/review, which is the whole point. (3) Leave the contradiction and treat 0.5.0 as an exception — rejected; an unstated exception in the source-of-truth spec is exactly the drift the framework exists to prevent.

## 2026-07-05 — Structural spec-graph validation: birth gates + blocking downstream lane audit
**Decision.** pdeq 0.6.0 adds *structural correctness* enforcement, split across two features. `product/spec-structure.md` (new) adds authoring-time **birth gates**: a three-way kickoff triage (update / new presentation of an existing feature / genuinely new feature), a mandatory read-existing-specs + overlap check before minting a new product spec, and an explicit "read the lane's `AGENTS.md` first" step on every kickoff lane. `product/lane-discipline.md` (extended) adds a **blocking structural content check** (`scripts/audit-structure.sh`): high-precision content-class detection (presentation/interaction, technical/construction, platform-as-product) on product specs, plus downstream scanning (engineering bleed in design specs; product-requirement *definitions* in engineering specs). Shared scan primitives moved to `scripts/lib/lane-scan.sh`; `audit-lanes.sh` refactored to source it with byte-identical behavior.
**Context.** A postmortem (the "coffee-shop" `views.md` incident) showed pdeq's audits verify the spec graph is *internally consistent* (every slug resolves) but never *structurally correct* (right kind of spec, right lane, not a duplicate). A GUI presentation of an already-specified ordering feature was mis-framed at kickoff as a new product feature, spawning a platform-specific, duplicate, engineering-leaking product spec that passed every consistency check and survived a full epic and ~12 commits before human review caught it. All four failure modes (mis-placed shared spec, duplicate spec, engineering-in-product, wrong-lane routing) were structural and invisible to existing tooling.
**Rationale.** The birth gates catch the errors at the cheapest point — before any slug is minted and propagates — which is why the correction cost (the postmortem's failure #4: retiring 44 stamped slugs by hand) is addressed by *prevention*, not new correction tooling. The blocking check is a separate script from the warn-only `audit-lanes.sh` (mirroring how blocking `audit-traceability.sh` and warn-only `audit-lanes.sh` already coexist) so the lexical backstop's warn-only contract stays byte-for-byte intact and the two enforcement strengths are legible at the hook level. Dogfooding on pdeq's own tree immediately surfaced a false positive ("click through a mockup" in `product/visualize.md`), so `click`/`scroll` were dropped from the blocking gesture defaults — the intended tuning loop, keeping the blocking set narrow and letting breadth come from project `laneAudit` terms and the advisory Lane Reviewer.
**Alternatives considered.** (1) One combined feature — rejected; applying the very triage gate being built, lane bleed *within* a spec (lane-discipline) and structural correctness *of the graph* (spec-structure) are distinct concerns, so they are two features. (2) Add content-class checking as a mode of `audit-lanes.sh` — rejected; that script is wired `|| true` (warn-only) and the blocking check needs the inverse, so a separate hook step without `|| true` is required. (3) Generic construction-word detection (`class`, `function`) in the blocking defaults — rejected; too false-positive-prone for a gate, left to Layer 2. (4) A similarity/dedup script for the overlap check — rejected; the user chose the agent-judgment version (mandatory + announced, no new tooling).
## 2026-07-05 — Blocking-on-bump with escape hatch; prevention-only, no slug-remap tooling
**Decision.** Two scoping calls for 0.6.0. **(a) Enforcement rollout:** the structural check is enforcement-*on the moment a consumer bumps the submodule pin* — no default-off opt-in toggle — with `PDEQ_ALLOW_DRIFT=1` as the single-commit escape hatch. `migrations/0.6.0.md` is `breaking: true`, loudly warns, and runs the check in report mode so a consumer sees exactly what will block their next commit. **(b) Slug tension:** the feature ships **no** remap/rename tooling and no provisional-slug state; slug permanence is preserved, and a structurally-wrong spec caught after slugs propagate is fixed by the existing manual retire-and-remint convention. Prevention at authoring time is the sole mechanism (`NFR-spec-structure-prevention-first`, `AC-spec-structure-no-remap-tooling`).
**Context.** 0.5.0 deliberately shipped lane discipline warn-only and left bleed cleanup as a project-owned follow-up, so real installs are known to carry bleed. Flipping warn→block is therefore breaking. Separately, the postmortem's failure #4 (permanence made a late structural fix expensive) invited a "draft slug" state or a `/pdeq-remap` command as possible remedies.
**Rationale.** Blocking-on-bump was chosen (user decision) over a default-off toggle so lane bleed cannot silently persist behind a flag nobody flips; the escape hatch makes the transition survivable without weakening the default. Scripts, hooks (`core.hooksPath` into the submodule), and command/`AGENTS.md` text all auto-propagate on the pin bump, so the migration carries no content — only the version contract, the config seed, and the breaking-change preview. Prevention-only was chosen (user decision) because a strong birth gate makes late-caught structural errors rare enough that correction tooling is not yet warranted; a draft-slug state is the most invasive change to the slug model and is largely redundant once the birth gate is strong.
**Alternatives considered.** Rollout: (1) opt-in toggle default-off for existing installs (non-breaking) — rejected by the user in favor of stronger enforcement; (2) migration auto-cleans bleed before enforcing — rejected; auto-editing consumer specs is risky and can't safely fix structural bleed anyway. Slug tension: (1) a `provisional` slug state renamable until stamped downstream — deferred as over-invasive; (2) a tooled `/pdeq-remap` retire-and-remint command — deferred to a future feature if late-caught errors prove common.

## 2026-07-06 — `laneAudit.exclude`: per-project exclusion of domain-legitimate default terms
**Decision.** pdeq 0.7.0 adds `laneAudit.exclude` to `pdeq.json` — a list of default red-flag terms a project has judged domain-legitimate, which the deterministic lane checks strip before matching (so they neither warn nor block), while a non-excluded flagged term on the same line still flags. Implemented by extending `pcre_scan` (in `scripts/lib/lane-scan.sh`) to strip a `PDEQ_EXCLUDE_RX` env pattern after the existing slug strip; `audit-structure.sh` and `audit-lanes.sh` compute it from config and export it. Non-breaking (opt-in), advisory `migrations/0.7.0.md`, `VERSION` → 0.7.0.
**Context.** Shipping 0.6.0's blocking structural check exposed a gap: `laneAudit` could only *add* red-flag terms, never *exclude* a default. Dogfooding the upgrade on the shepherd project made it concrete — shepherd is a code-review tool that legitimately names the languages it supports (TypeScript, Python, …) and the operating systems it targets (macOS, Linux, Windows). The blocking defaults flag those correct, domain-legitimate mentions, and the only escapes were rewording correct specs (lossy) or `PDEQ_ALLOW_DRIFT=1` on every commit (not viable long-term).
**Rationale.** Reusing the slug-strip mechanism makes exclusion *surgical for free* — only the excluded term is removed from the line, so exclusion cannot blanket-silence a line that also carries real bleed (`NFR-lane-discipline-exclude-surgical`). Passing the pattern via `PDEQ_EXCLUDE_RX` (env, not a positional arg) means every existing `pcre_scan` call honors it with no signature change, and an unset variable is a no-op, so back-compat holds by construction. Exclusion applies to both deterministic checks (warn + block) but never to the advisory Lane Reviewer, which keeps reasoning about context — so a project's exclusions speed the deterministic net without blinding the principle-level review.
**Alternatives considered.** (1) Reword shepherd's specs to avoid the terms — rejected; makes correct specs vaguer to satisfy a lint, and would recur for every domain-legitimate term. (2) Excel only via `PDEQ_ALLOW_DRIFT=1` — rejected; per-commit, so it would have to be used forever. (3) Make exclusion a whole-line allow (skip any line containing an excluded term) — rejected; that lets an excluded term smuggle real bleed past the check on the same line. (4) Apply exclusion only to the blocking check, not the warn-only backstop — rejected; a term a project has declared in-lane should not warn either, and one shared mechanism is simpler.

## 2026-07-06 — Platform conformance audit: a new advisory quality reviewer (kickoff)
**Decision.** Kicked off a new feature, `conformance` (`product/conformance.md` + `engineering/cli/conformance.md` + `qa/cli/conformance.md`), for an **advisory** per-platform conformance audit — the fourth pdeq quality reviewer alongside Reviewer, Consistency Checker, and Lane Reviewer. It reasons about a platform's source against that platform's specs and emits a four-quadrant report: **fulfilled** / **unfulfilled** / **incorrectly fulfilled** (verdicts per requirement) plus **undocumented** behavior (reverse traceability). Surfaced as `/pdeq-conform <platform> [feature]`. Realized as agent prose (a Conformance Reviewer role in root `AGENTS.md` §Quality Subagents + a `pdeq-rules/commands/pdeq-conform.md` command file), not a shell script. Never wired into hooks — it is non-gating like the Lane Reviewer, and complements (does not replace) the deterministic coverage phase in `scripts/audit-traceability.sh`.
**Context.** The user asked whether pdeq's audit surfaces un-implemented requirements, per-platform fulfilment, *incorrectly* fulfilled requirements, and undocumented features. The deterministic traceability audit covers the first (marker-presence coverage, grace-gated) and partially the second, but structurally cannot do the last two: a marker is a *claim*, never a verification, so incorrectly-fulfilled code passes it; and the scanner is requirement-driven, so undocumented code has nothing to match. Those two are semantic judgments — the domain of an agent reviewer, not a grep.
**Rationale — why a new feature, not a fold into `code-mapping.md`.** Considered bundling this into `code-mapping.md` the way `lane-discipline.md` bundles its deterministic backstop + advisory Lane Reviewer. Rejected: in lane-discipline both layers enforce the *same* predicate (no lane bleed), so the reviewer is the semantic mirror of the grep. Here the predicates differ — code-mapping's audit enforces "markers present & valid"; conformance enforces "code behaves as specified" and "no undocumented behavior." A requirement can pass code-mapping (valid marker) yet be incorrectly fulfilled, and undocumented behavior has no marker at all. So conformance is a distinct, broader concern that *consumes* code-mapping's outputs (Code Map + index) as its seed rather than re-specifying them. Keeping code-mapping's "lexical, deterministic, gating" identity clean. Overlap check against all seven existing product specs found no material overlap.
**Scope calls.** (1) Advisory / never-gating — semantic LLM judgment must never block a commit (Lane Reviewer precedent). (2) Skipped the design lane — consistent with its siblings (`code-mapping`, `lane-discipline`, `spec-structure` have no design spec; only the interactive `migrations` does); the report format is an engineering concern. (3) v1 scopes requirement verdicts to `FR-`, treating `NFR-`/`AC-` as best-effort (harder to judge from source alone). (4) Whole-platform read by default, optional per-feature narrowing via the command's `[feature]` argument. (5) Findings are ephemeral in v1 — no persisted accepted-divergence list (a possible future mirror of `laneAudit.exclude`). (6) Product spec is platform-neutral (conformance auditing applies to any platform); design/eng/qa live under `cli/`.
**Alternatives considered.** (1) Fold into `code-mapping.md` — rejected (different predicate; see rationale). (2) Make it a deterministic script — rejected; correctness and reverse-traceability are semantic and cannot be graphed by a lexical scan. (3) Make it gating — rejected; judgment-based verdicts with inherent uncertainty must not block merges. (4) Add a design spec for the report format — rejected; matches no sibling reviewer feature, and the format is engineering's concern.
## 2026-07-06 — First conformance-audit dogfood found (and fixed) a real cleanup bug
