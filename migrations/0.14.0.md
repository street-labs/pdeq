# Migration 0.14.0 — Lane guides consolidation

## Context

Pdeq 0.14.0 adds **lane guides**: a config-driven, harness-agnostic way to attach a per-lane "guide" file of skills, architecture, or guidelines that the lane agent reads before authoring specs in that lane. A consumer declares guides in `pdeq.json` under a new `laneGuides` object (lane id → path relative to `specsRoot`); the installer validates the paths and warns on misses; the framework's canonical agent templates tell each lane agent to read its guide when configured. Lane guides are distinct from standing specs (project-wide) — they are lane-scoped, surfaced at authoring time, and a single file may be both.

**Why a migration.** Before lane guides, a consumer's only per-lane customization surface was asymmetric: Claude consumers could append project-specific prose below the `@import` in a lane `CLAUDE.md`; Codex/Pi consumers got a symlink with no append slot. Some consumers also kept lane-specific architecture or convention docs as standalone markdown in a lane folder, outside the spec graph. This migration brings that existing lane-specific content into the declarative `laneGuides` mechanism so every harness gets the same per-lane customization, the declarations survive re-installs, and `/pdeq-status` can report them.

**This migration is advisory** (`breaking: false`). It seeds no scaffolding (the installer never stubs a guide file). Its semantic pass scans for lane-specific content, consolidates it into `<lane>/GUIDE.md` files, declares them in `pdeq.json` `laneGuides`, and pares the sources. A project that skips it stays conformant — no audit blocks on `laneGuides` being absent. A project with no lane-specific content to consolidate sees a no-op with a summary line reporting zero candidates.

**What ships in the diff for a consumer:**
- New: `<lane>/GUIDE.md` for each lane where the migration found and consolidated lane-specific content.
- Modified: `pdeq.json` gains a `laneGuides` object mapping each consolidated lane to its guide path.
- Modified (pared): a project-owned lane agent override file (`<lane>/CLAUDE.md` or `<lane>/AGENTS.md`) is reduced to its framework import line when its appended content moved into a guide.
- Possibly removed: a standalone non-spec lane doc whose full content moved into the guide (only when the doc had no remaining purpose; flagged in the summary, not silently dropped).

### Prompt

You are migrating a pdeq consumer project to version 0.14.0, which adds **lane guides**: a declarative, harness-agnostic way to attach a per-lane guide file that the lane agent reads before authoring. A consumer declares guides in `pdeq.json` under a `laneGuides` object mapping a lane id (`product`, `design`, `engineering`, `qa`, `roadmap`) to a file path relative to `specsRoot`. Your job is the semantic pass: find lane-specific content already living in the project, consolidate it into `<lane>/GUIDE.md` files, declare them in `laneGuides`, and pare the sources. The canonical lane templates already tell each lane agent to read its guide — you do not edit the framework files.

**Step 1 — Identify project-owned lane agent override files.** For each lane (`product`, `design`, `engineering`, `qa`, `roadmap`):
- `<lane>/CLAUDE.md` — if it is a **real file** (not a symlink), it is project-owned. Its first line is normally a `@`-import of the framework; any content below that import is project-specific append-slot content — the primary candidate to move into a guide.
- `<lane>/AGENTS.md` — if it is a **real file** (not a symlink to `.pdeq/<lane>/AGENTS.md`), it is project-owned and treated the same way. If it is a symlink to the framework file, it is **not** project-owned and must not be edited.

If a lane has no project-owned override file, there is no append-slot content to move for that lane — continue to Step 2.

**Step 2 — Scan for standalone non-spec lane docs.** In each lane folder, look for markdown files that are **not** feature specs — i.e. they carry no `FR-`/`NFR-`/`AC-` slugs and are not `AGENTS.md`/`CLAUDE.md`. These are typically architecture baselines, testing strategies, design-system references, or convention guides (e.g. `engineering/architecture.md`, `qa/snapshot-testing.md`, `design/design-system.md`). They are candidates to become (or be consolidated into) that lane's guide. Do not touch feature spec files (those with slugs) — they are the spec graph, not guide material.

**Step 3 — Scan for lane-scoped standing specs.** Read `project.md`'s Standing specs table. A standing spec whose `governs:` scope is a single lane (e.g. "engineering architecture baseline", "qa testing strategy") rather than the whole project is a candidate to **also** become a lane guide. A file can be both a standing spec and a lane guide — promoting it does not remove it from the standing-specs manifest.

**Step 4 — Consolidate into lane guides.** For each lane where Step 1, 2, or 3 found a candidate, consolidate the lane-specific content into a single `<lane>/GUIDE.md`:
- If the lane already has an entry in `pdeq.json` `laneGuides` pointing at a resolving file, **merge into that existing guide** — do not create a second guide file or a second `laneGuides` entry.
- Otherwise create `<lane>/GUIDE.md` and add a `laneGuides` entry: `"<lane>": "<lane>/GUIDE.md"` to `pdeq.json`. If `pdeq.json` has no `laneGuides` object, add one. Preserve existing config fields and formatting.
- When merging multiple sources into one guide, deduplicate — do not copy the same convention twice. Lead with a one-line `> Lane guide for <lane>.` pointer line so a reader knows what the file is.
- For a lane-scoped standing spec (Step 3), do **not** copy its body into `GUIDE.md` — instead add the standing spec's own path to `laneGuides` (the file is already the guide content; no new `GUIDE.md` is created for it). This keeps one source of truth.

**Step 5 — Pare the sources.**
- For a project-owned lane override file (Step 1): remove the content that moved into the guide, leaving only the framework `@`-import line (and any genuinely cross-lane content that does not belong to this single lane — but prefer moving it to `project.md` or flagging it; do not leave lane-specific prose behind). If the file becomes exactly one line (the import), that is the intended end state.
- For a standalone non-spec lane doc (Step 2) whose **full** content moved into `GUIDE.md`: remove the now-empty/duplicate file only if it has no remaining purpose; otherwise leave it and flag it in the summary so a human can adjudicate. Never delete a file that still holds unique content not captured in the guide.
- Do not modify a standing spec's body or frontmatter (Step 3 source) — you only added its path to `laneGuides`.

**Step 6 — Idempotency check.** A lane already present in `laneGuides` with a resolving guide is **not** re-processed: do not rewrite its `GUIDE.md`, do not re-scan its override file, do not duplicate its entry. A project-owned override file already reduced to a single import line is left alone. If every lane is already in this state, make no changes and end with a summary reporting zero candidates.

**What NOT to change:**
- Do not edit a symlinked `<lane>/AGENTS.md` (the framework file) or any file inside `.pdeq`.
- Do not edit feature spec files (those carrying `FR-`/`NFR-`/`AC-` slugs), `index.md`, `glossary.md`, `decisions.md`, `decisions-pending.md`, or `project.md`'s authored sections. The standing-specs manifest in `project.md` is read-only here.
- Do not mint slugs, roadmap entries, or new standing specs. (Adding an **existing** standing spec's path to `laneGuides` is allowed; minting new ones is not.)
- Do not invent guide content — only consolidate content that already exists in the project. If a lane has no candidates, it gets no guide.

Make NO changes to files that are already clean. Silence on a file means "already conformant."

End with exactly one summary line of the form: `laneGuides: <N> lanes configured (consolidated: X, standing-promoted: Y, candidates flagged: Z), files created: A, files pared: B, files removed: C` — where `consolidated` counts lanes where append-slot/standalone-doc content moved into a guide, `standing-promoted` counts lane-scoped standing specs added to `laneGuides`, and `candidates flagged` counts items you left for a human to adjudicate. Beneath the summary line, if you flagged any candidates or removed any files, give a short bulleted list of them with locations.
