# Migration 0.5.0 — Lane discipline

## Context

Pdeq 0.5.0 adds two-layer lane-discipline enforcement: a deterministic lexical backstop (`scripts/audit-lanes.sh`, now project-tunable via a `laneAudit` object in `pdeq.json`) and an agent-run Lane Reviewer that reasons about structural bleed. See `product/lane-discipline.md`.

The change is **non-breaking**: `laneAudit` is optional, the backstop's built-in defaults are preserved, and a project stays conformant without doing anything. This migration exists to *propagate* the feature into an existing project rather than to repair a broken contract:

1. It seeds an empty `laneAudit` scaffold into `pdeq.json` so the tunable term list is discoverable and ready for the project to fill in with its own vendors, protocols, platforms, and libraries.
2. It runs the Lane Reviewer over the project's existing product specs **in report-only mode** — it surfaces where current specs already carry design/engineering/platform bleed and suggests `laneAudit` terms, but changes nothing. Acting on the findings is a deliberate follow-up the project owns.

What changes in the consumer's diff: `pdeq.json` gains a `laneAudit` block (only if absent). No spec files are modified by this migration.

## Mechanical

```shell
# Seed an empty laneAudit scaffold into pdeq.json, only if no laneAudit key is
# already present. Idempotent: a second run, or a run against a project that
# already configured laneAudit, makes no change. Uses inline python3 (no jq),
# matching the repo convention for reading/writing pdeq.json.
python3 - <<'PY'
import json

path = "pdeq.json"
with open(path) as f:
    data = json.load(f)

if "laneAudit" in data:
    print("laneAudit already present in pdeq.json — no change")
else:
    data["laneAudit"] = {
        "vendors": [],
        "protocols": [],
        "platforms": [],
        "libraries": [],
    }
    with open(path, "w") as f:
        json.dump(data, f, indent=2)
        f.write("\n")
    print("seeded empty laneAudit scaffold into pdeq.json")
PY
```

## Semantic

### Files

- `product/**/*.md`

### Prompt

You are the **Lane Reviewer** (see the root `AGENTS.md` §"Quality Subagents" → Lane Reviewer for the full contract). Review every loaded product spec for design, engineering, and platform bleed — content that belongs in the design, engineering, or QA lane rather than in a platform-neutral product spec.

**What to look for.** Reason about the meaning and structure of the text, not just keywords. Flag: vendor names; protocol or algorithm names; a host or platform treated as if it were the product; library or framework names; concrete surfaces (command names, flags, exit codes, env vars, file paths, ports, redirect URIs); implementation mechanisms (secret stores, file permissions, background polling); and testing terms. Flag structural bleed even when it names no obvious keyword (e.g. a requirement phrased as a protocol exchange, or "subsequent invocations" treating one host as the product).

**What to change.** Nothing. This is a **report-only** pass. Do **not** edit, reword, reformat, or rename anything in any file. Do not create files.

**What to produce.** Output a single Markdown table with one row per finding and these columns: `File | Line | Flagged text | Category | Severity | Suggested rewording`. Use severity `violation` for real lane violations and `allowed: <reason>` (e.g. `allowed: overview context`, `allowed: per-host NFR constraint`) for mentions that are legitimate in context. After the table, if you found concrete vendor/protocol/library words that a keyword scan would miss, add a short "Suggested `laneAudit` additions" note listing the category and terms the project could add to `pdeq.json`.

**Conformance.** If a spec has no findings, include no rows for it — silence means already conformant. Make no change to any file regardless of findings.

**Finish** with exactly one summary line: `reviewed <M> files, updated 0` where `<M>` is the number of product specs you read. The `updated 0` is mandatory — this pass never edits.

## Notes

- `breaking: false` because a consumer stays conformant without running this migration; the backstop works with built-in defaults the moment the submodule is bumped, and the review is advisory. The migration is present because pdeq's commit-msg gate treats any MINOR version bump as breaking and requires a matching migration file — and because the seed + review are genuinely useful on adoption.
- The Mechanical block reformats `pdeq.json` with two-space indent when it adds the scaffold. This is a one-time, reviewable change; the block is still idempotent (the second run finds `laneAudit` present and exits without writing).
- The Semantic pass is report-only by design (`AC-lane-discipline-update-review-no-edit`): product specs are the source of truth, and auto-rewording requirements risks changing their meaning. The project applies the reported fixes deliberately.
