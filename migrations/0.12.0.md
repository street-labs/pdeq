# Migration 0.12.0 — Project orientation

## Context

Pdeq 0.12.0 adds **project orientation**: every pdeq project gets a `project.md` at its specs root — the skinny on what the project is, its platforms and tech stack, the **standing specs** every builder must respect, and how to operate within it. A *standing spec* is a cross-cutting spec (style guide, architecture baseline, security baseline) marked `standing: true` in its frontmatter; `project.md`'s Standing specs table is the manifest of them. The coordinator reads `project.md` at the start of every implementation session.

**This migration is advisory** (`breaking: false`). It seeds `project.md` for projects that lack one and offers a semantic pass that consolidates project-specific content that has organically accumulated in the framework agent file (or a harness override file) into `project.md`. A project that skips it stays conformant — no audit blocks on `project.md`'s absence in v1.

**What ships in the diff for a consumer:**
- New: `project.md` at the specs root (skeleton, seeded by `scripts/seed-project-md.sh`).
- New: `scripts/seed-project-md.sh` (installed automatically when the `.pdeq` submodule is bumped).
- Possibly modified: the project-owned agent file (see Semantic) pared of project-specific content now living in `project.md`.

## Mechanical

Seed `project.md` from the shared skeleton. Idempotent: a no-op when the file already exists.

```shell
# Implements: FR-project-orientation-migration-seeds, AC-project-orientation-migration-idempotent
# Seed project.md at the specs root. The script resolves the specs root from
# pdeq.json (or PDEQ_SPECS_ROOT) and writes a skeleton only if absent.
./scripts/seed-project-md.sh
```

## Semantic

### Files

- `project.md`
- `AGENTS.md`
- `CLAUDE.md` (if present)
- `pdeq.json`
- `README.md` (if present)

### Prompt

You are migrating a pdeq consumer project to version 0.12.0, which adds project orientation.

`project.md` is the project's orientation file: a short, living document with sections **What this is**, **Platforms**, **Tech stack**, **Standing specs** (a table), and **How to operate**. The mechanical block just seeded a skeleton (with TODO placeholders) if one did not exist. Your job is the semantic pass: fill in the skeleton from project signals, and consolidate project-specific clutter out of the framework agent file.

**Step 1 — Seed the authored sections.** For each of **What this is**, **Platforms**, **Tech stack**, and **How to operate** in `project.md`: if the section still contains its TODO placeholder, fill it in from `pdeq.json` (platforms), the project `README.md` (identity, stack), and detected repository signals (language, frameworks, build tooling). Leave a section alone if a human has already authored it — do not overwrite real content. Keep each section short: a few sentences or a short list. The **Standing specs** table is left empty by this step unless the project already has specs marked `standing: true` in their frontmatter, in which case add a row for each.

**Step 2 — Identify the project-owned agent file(s).** Determine which agent files this *project* owns and may edit:
- `AGENTS.md` — if it is a **real file** (not a symlink to `.pdeq/AGENTS.md`), it is project-owned. If it is a symlink to `.pdeq/AGENTS.md`, it is the framework file and **must not be edited** — skip it.
- `CLAUDE.md` — if present and a real file (a harness override wrapper that `@`-imports the framework), it is project-owned.

If neither is project-owned (a clean consumer with a symlinked `AGENTS.md` and no `CLAUDE.md`), there is nothing to pare — stop after Step 1 and end with the summary line.

**Step 3 — Scan for project-specific accumulation.** In each project-owned agent file, look for content that is **project-specific** rather than framework rules:
- Project identity, "what this is" prose, product descriptions.
- Tech stack notes, language/framework choices, build commands.
- Project-specific conventions or guidance that duplicates or conflicts with what now belongs in `project.md` or a standing spec.

**Step 4 — Consolidate.** Move project-specific identity/stack/operating content into the matching `project.md` section (merging, not duplicating — if `project.md` already says it, remove the duplicate from the agent file). Where the content is a cross-cutting convention worth keeping as a spec (e.g. a style rule, an architecture constraint), **do not mint a standing spec unprompted** — flag it as a candidate in your summary so a human can kick it off via `/pdeq-kickoff` with `standing: true`.

**Step 5 — Pare and flag.** Remove the moved/duplicate content from the project-owned agent file, leaving framework rules intact. Where a removal would discard a **conflict or duplicate** that a human should adjudicate (e.g. two different statements of the same convention that disagree), **do not silently drop it** — flag it explicitly in your summary with the location and the conflict.

**What NOT to change:**
- Do not edit a symlinked `AGENTS.md` (the framework file).
- Do not mint standing specs, slugs, or roadmap entries.
- Do not touch `index.md`, `glossary.md`, `decisions.md`, `pdeq.json`, or any spec files.
- Do not overwrite authored `project.md` sections — only fill placeholders.

Make NO changes to files that are already clean. Silence on a file means "already conformant."

End with exactly one summary line: `updated N of M files`, plus, if you flagged any candidate standing specs or conflicts, a short bulleted list of them beneath the summary line.
