# Migration 0.7.0 — `laneAudit.exclude`

## Context

Pdeq 0.7.0 adds `laneAudit.exclude` to `pdeq.json`: a list of **default red-flag terms a project has judged domain-legitimate** — a platform it must run on, a language it supports, a first-class domain noun. The deterministic checks (both the warn-only backstop and the blocking structural/downstream checks) strip these terms before matching, so they neither warn nor block. Stripping is surgical — a non-excluded flagged term on the same line still flags. See `product/lane-discipline.md`.

This is the principled answer to the 0.6.0 limitation that `laneAudit` could only *add* terms, never *exclude* a default — which forced projects with legitimate domain vocabulary (e.g. a code-review tool naming the languages it supports, or a desktop app stating the operating systems it targets) to either reword correct specs or use `PDEQ_ALLOW_DRIFT=1` on every commit.

**This change is non-breaking.** `laneAudit.exclude` is optional; a project that declares none behaves exactly as at 0.6.0. The new behavior reaches a project automatically when it bumps the submodule pin (the edited `scripts/lib/lane-scan.sh` and the two audit scripts are symlinks). This migration exists for the version contract and to make the new key discoverable — it changes no files.

## Notes

- **Why advisory.** `laneAudit.exclude` is opt-in and back-compatible, so a consumer stays conformant without acting. Per the advisory-migration class (see `product/migrations.md`), it rides the lineage-breaking MINOR bump without being consumer-breaking.
- **How to use it.** Add the terms to `pdeq.json`, e.g. `"laneAudit": { "exclude": ["macOS", "Linux", "Windows", "TypeScript", "Python"] }`. Exclusion is exact and word-boundary; it applies to every deterministic check but never to the advisory Lane Reviewer, which keeps reasoning about context.
